# Annotation Protocol V2

Phase 1.6.1 uses two source frames and two independent reviews per frame to measure agreement in semantic annotation and raw measurement. This is a new annotation format. The version 1 dataset, model, coordinate conventions and scoring stay under the existing experiment protocol. The owner distributes only the ZIP produced for each reviewer. The builder takes the three reviewer sections below and adds the packet's assigned pass order. [Retest plan](ANNOTATION_RETEST_PLAN.md) · [Version 1 experiment](EXPERIMENT_PROTOCOL.md)

## Reviewer instructions

Use only the supplied frame and the guide for your current pass. Open frame.png in a viewer with pixel coordinates. Check coordinates at native size or with accurate zoom. X increases rightward and Y downward from the top left. Black rectangles cover interface text. Mark automap pixels except where the guide explicitly requests a scene position.

Keep packet_id, protocol_version, frame_sha256 and resolution unchanged. Each response begins as a blank template. For each pass, start the clock when you open its guide. Record elapsed_minutes including image inspection and JSON entry. Use up to eight active minutes per pass. Fill time_limit_reached and each search_complete field with true or false. If you reach the limit, save the measurements you have and note unfinished sections. Start the second pass from its blank template and the source image without consulting your saved first response. Return both JSONs separately.

Use OBSERVED for a visible, localizable feature. Use UNKNOWN for insufficient evidence and AMBIGUOUS when multiple readings are plausible. Unresolved positions or directions use null and a brief evidence note. Record an estimated radius in native pixels for each observed point and for each endpoint of a measured segment. A single error_px for a segment bounds the marking error of either endpoint. Radii describe marking uncertainty from blur, overlap or an indistinct trace. Empty lists mean you recorded no instances. Use notes for obstacles and incomplete searches.

In each pass, look across the visible automap for distinct colored glyphs drawn on wall traces or gaps. Exclude spell effects, player markers, lighting and interface icons. For the wall sample, mark up to eight nearest visible straight traces to the fixed image midpoint (960, 540), judged by the trace midpoint. Keep trace fragments separate at a corner or interruption. If you cannot assign all of them in your pass, record why.

A point mark has status, px, error_px and note. Example `{"status":"OBSERVED","px":[810,505],"error_px":4,"note":"blue automap cross"}`. A glyph record uses id, status, appearance, center_px, segment_px, error_px and note. Appearance is a short visible description such as "yellow vertical bar". Use two endpoints along the measured span of the glyph on its wall trace. Estimate the centre too. If only a centre is readable, use null for segment_px and describe the obstruction. Keep the marker extent separate from the surrounding wall. Mark each physical glyph once even when two regions share it.

## Semantic pass

Fill semantic.json. Measure the current player automap marker in player. The four marks in entrance are independent. staircase_scene is the centre of the recognizable physical stair threshold in the scene. automap_glyph is the visible automap symbol only if this frame supports identifying it as the entrance. arrival_room_center is a defensible centre of the bounded arrival-room footprint on the automap. It requires enough visible boundaries to identify its extent and evidence associating that footprint with the stair entrance. player_arrival is the player automap position only when the image itself supports the player being at arrival. Player, glyph, stair and room centre require their own evidence.

orientation is the direction along the visible entrance throat from the arrival-room interior toward the staircase side in the automap plane. Mark the two endpoints of this visible centreline in orientation.segment_px and give an endpoint radius. Order them interior to staircase when that polarity is visible. Use a directed sector N, NE, E, SE, S, SW, W or NW, centred at 0°, 45° and so on clockwise from map-up. If the throat is clear but either endpoint could be the staircase side, use the corresponding two-way axis NS, NE_SW, EW or NW_SE. Use UNKNOWN or AMBIGUOUS and a null direction when the throat or its association with the entrance is unclear, or when endpoint uncertainty could change the sector or axis. An observed centreline can still be recorded with a null direction. Interior room shape, a scene-only stair angle and a colored symbol alone cannot establish this orientation.

In regions, record candidate outlines you can localize, including possible enclosed structures. Each record has id, class (ROOM, ENCLOSED_FEATURE or UNRESOLVED), center (a point mark), perimeter (COMPLETE, INCOMPLETE, UNKNOWN or AMBIGUOUS) and note. Use ROOM when the visible outline and opening or floor evidence support a room footprint. If an enclosure may be either architectural detail or a room, use UNRESOLVED. Use the centre only for a reproducible footprint or a clearly localizable candidate, and explain which it is.

In walls, record the wall sample with id, room_id, segment_px, error_px, status (CONTINUOUS, INTERRUPTED or AMBIGUOUS) and note. Assign room_id only for a supported boundary of a ROOM. Keep a sampled trace outside the semantic room graph with a null room_id and an explanation. Record the common glyph search in markers using the glyph format.

In openings, separately assess any boundary breach or candidate passage. Use id, marker_id (or null), room_id (or null), segment_px (or null), error_px (or null), geometry (OPEN_GAP, WALL_AT_MARK, UNKNOWN or AMBIGUOUS), passage (CONFIRMED, UNKNOWN or AMBIGUOUS), destination_room_id (or null), frontier_direction (one directed sector or null), and note. A gap needs a visible interruption of the wall forming a coherent opening. CONFIRMED passage requires visible geometry supporting continuity across a boundary, such as a clear threshold with floor or corridor continuation. Color alone or a missing line alone is insufficient. Keep the gap and traversability assessments independent. A frontier direction requires a confirmed visible departure heading into unmapped or clipped continuation. A missing adjacent centre alone does not establish a frontier. A confirmed physical opening is one record even when observed from both sides. In connections, record a pair only for two identified ROOM footprints visibly joined by a confirmed passage. Each entry uses rooms (a pair of IDs) and opening_id. Either endpoint orientation of the pair is fine.

In terminal_assessments, use room_id, status, departure_opening_ids and note. Use TERMINAL only for a completely observed ROOM with a fully readable perimeter and one confirmed departure, with every other possible exit ruled out by visible evidence. Use ONE_DEPARTURE_ONLY if one departure is confirmed but there are unreadable or incomplete boundaries. Use NON_TERMINAL for two or more confirmed departures. Use INCOMPLETE for incomplete outlines with no confirmed departure and UNKNOWN or AMBIGUOUS when the evidence is otherwise insufficient. Enclosed features require no terminal claim. A visually supported terminal room with an observed opening and no confirmed destination may be recorded as such. State what is visible and leave missing graph links unspecified.

## Raw pass

Fill raw.json. Measure the current player automap marker in player. For walls use id, segment_px, error_px, status (CONTINUOUS, INTERRUPTED or AMBIGUOUS) and note. Record the endpoints of each visible straight trace in the wall sample. For a visible interruption, mark the visible fragments separately and note the interruption. Avoid filling in any unseen interval. A trace can be marked with ambiguous status if its pixels are identifiable but its nature is uncertain.

Record the glyph search in markers using the common glyph format. Include visible appearance and localization uncertainty. Record the same native coordinate system for every mark. Player-relative offsets are calculated by subtracting the marked player point from each visible endpoint or centre. If the player is unresolved, the absolute marks are still usable. Describe obstructions or alternative readings in notes.

## Owner-side interpretation

Keep the two V2 returns and derived comparisons separate from V1. The V2 entrance centre is the proposed V1 origin. Orientation uses the same eight sectors and four axial names, with a specified entrance-facing convention for V2. This convention is a test definition. V1's null entrance-orientation fields provide no established direction polarity to migrate. The V2 room graph can be summarized from confirmed rooms and links. A V1 structural terminal feature requires exactly one declared link or supported outgoing frontier as well as a V2 terminal decision. A terminal claim backed by visible evidence alone can remain in the V2 audit when the departure cannot be represented. Record the failed projection as a representation limitation. Keep source pixels, candidate enclosures, marker extents and interrupted walls in the V2 record. The raw return contains no room or connection assertions.
