# Feasibility

**Go for a small offline experiment after Phase 1 approval. Hold D2R compatibility and overlay work pending independent D2R evidence.** A partial layout can narrow the candidate set, and several candidates can support the same target direction. The useful question is how often the direction agrees while the target is still hidden.

## Candidate algorithms

| Approach | Feasibility and role |
| --- | --- |
| A. Template matching | Anchor a visible room or connector, normalize translation and scale, and compare only visible segments to known signatures. Enumerate plausible grid alignments when orientation is ambiguous. Respect authored orientation variants. Use masked distances and permit missing lines. Repeated corridor fragments, clipped corners, scale errors and effects in captured images can make matches non-unique. Start with geometry-level signatures. Test image alignment later using paired images. |
| B. Graph matching | Represent observed rooms and explicitly visible links as an embedded, rooted graph. In the first experiment, index candidates by entrance-relative grid coordinates and compare compatible cells and connectors. Use general subgraph search only if an unanchored graph proves necessary. Compare missing links only when the corresponding boundary is visible. Arbitrary topology matching adds search cost and produces ties for common corridors and branches. |
| C. Map fingerprinting | Use a hash map keyed by entrance orientation or a short visible neighborhood signature, with full comparisons after lookup. Spatial hashing maps relative coordinates to candidate features. Geometric hashing using relative segment offsets can help if the room origin is uncertain. Connectivity and neighborhood signatures can use degree and observed directional edges. Partial signatures collide, and noisy observations can miss a strict bucket. Keep a scan as the reference implementation. Add a compact posting list or partial signature bucket only if the measured cache size or scan cost warrants it. |
| D. Rule-based prediction | Encode a verified orientation constraint or learn a small empirical direction table from development maps. Evaluate each target using entrance geometry available to every method. The classic code supports a relationship between generator state and special preset orientation. Whether the target lies in a particular sector from the player is an empirical question. An instruction framed relative to a known waypoint is inapplicable to predicting that hidden waypoint. [Classic Catacombs placement](https://github.com/ThePhrozenKeep/D2MOO/blob/master/source/D2Common/src/Drlg/DrlgMaze.cpp#L630-L685) |
| E. Seed reconstruction | Defer. Partial geometry may correspond to many seeds, and a single output layout may represent multiple seeds. A rough 31-bit search, as assumed by one classic tool, means about 2.15 billion trials. Even at 100 microseconds each it would take about 60 hours on one worker before overhead, and 20 bytes per seed needs roughly 40 GiB. D2R seed mapping and effective entropy were not established. The classic Tower example uses substantial precomputation and much richer observations. [Tower seed experiment](https://github.com/emmericp/diablo2-maps#using-the-seed-finder), [index estimate](https://github.com/emmericp/diablo2-maps/blob/main/Dockerfile) |
| F. Hybrid prediction | Combine the embedded geometry match with the baseline's orientation information. Aggregate supported locations per target and derive direction mass from the candidate locations. Keep competing sectors and allow abstention. Candidate vote share is initially a score. Calibration on separate maps determines whether the score can be reported as confidence. This is the recommended experiment. |

A linear scan costs about `C × A × K` feature checks, where `C` is the reference count, `A` is the number of tested alignments, and `K` is the number of observable features. A packed set of 10,000 maps with 40 feature records at 16 bytes each would use 6.4 MB for records alone. Object and index overhead, candidate coverage, and achievable latency are still unknown. Measure them at 100, 1,000 and, if available, 10,000 reference maps before choosing a permanent representation.

## Risks and open questions

| Risk or unknown | Evidence needed |
| --- | --- |
| Classic-to-D2R layout drift | Independently labeled D2R fixtures for one build, mode and difficulty. Compare generated geometry and both landmark anchors on paired seeds only if seeds are already available through an authorized source. If seeds are unknown, evaluate directional transfer directly on held-out D2R observations. |
| Collision geometry differs from visible lines | Compare independently annotated automap geometry against projected reference features. Record which walls, doors and connectors survive crop, zoom, background and reveal behavior. |
| Early observations are ambiguous | Measure how many unique layouts and distinct target sectors share the first one to three rooms. Analyze irreducible disagreements among indistinguishable observations, and compare both targets against the orientation baseline. |
| Reference corpus misses common configurations | Measure nearest-candidate mismatch, no-match rate, coverage and results by entrance orientation. Use layout-disjoint holdouts and a reference-size sweep. A candidate set can agree while the true layout is absent. |
| Target locations or coordinates are mislabeled | Verify warp direction, destination and coordinate units, and distinguish the actual anchor from the room centre. Record labels from an independent observation or source when assessing generator compatibility. |
| More exploration may arrive after a target is visible | Report the eligible denominator at each step and track a fixed cohort across reveal stages. A result for geometry after discovery is a diagnostic. |
| Developer and runtime budgets | Run the CLI on the target hardware and measure matching latency and process peak working set. End-to-end CPU usage and drawing costs require a later approved runtime test. The local modern .NET SDK is missing. [Environment](../research/ENVIRONMENT.md) |

## Go and no-go criteria

1. **Algorithm gate.** Start Phase 1 after approval. Synthetic fixtures must cover known exact, probable, ambiguous and no-match cases, including conflicting hidden targets. The experiment must report deterministic results on layout-disjoint splits. A synthetic pass verifies the harness and behavior under the fixture assumptions.
2. **D2R utility gate.** The proposed product threshold per target is at least 70% correct four-sector bearings at 60% or more prediction coverage by three observed rooms. Require at least five percentage points of improvement over the entrance-orientation baseline at matched coverage, with the paired 95% interval for the difference above zero. A positive result applies only to the validated D2R build, mode, arrival and difficulty. Use the evaluation protocol to apply the thresholds. [Benchmark protocol](../benchmarks/PROTOCOL.md)
3. **Performance gate.** On the target machine, require p95 warm prediction latency below 100 ms and peak process working set under 100 MB at the reference size used for the result. Record cold load separately. Reserve the below-2%-CPU goal for a later end-to-end, change-triggered runtime measurement.
4. **Stop condition.** If D2R fixtures are unavailable, record a blocked D2R verdict alongside the synthetic or classic results. If reliable early predictions fail to clear the baseline at useful coverage, stop before implementing an overlay and report the observed information limit. Advancement for only one target would require agreement to narrow the objective.
